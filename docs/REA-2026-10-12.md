## 已观察到的机制

1. `main/src/services/player/player.ts:640-647` 从当前队列位置取后续 5 个可播条目交给引擎。`app/src/services/playerProxy/index.ts:185-245` 的 `setPreloadUrls` 按资源 ID 去重、移除旧任务、创建新任务。
2. `app/src/services/playerProxy/index.ts:248-313` 先满足当前播放曲目的前段缓存阈值，再按顺序为候选准备可播前段；满足此前置条件后才继续加载候选的完整内容。`mediaTask.ts:54-60` 把阈值设为 `256 KiB + 5 秒按码率计算的字节数`；未知码率使用 `800 KiB`。这是代码中的调度规则，不是本次网络抓包观察值。
3. `main/src/services/player/audioEffect/audioEffectManager.ts:16-51,70-95` 创建 AudioWorklet、等待 WASM 初始化握手（超时 10 秒），再按 `loadConfig → prepare(sampleRate, channels) → setEnabled` 切换处理；空配置关闭处理。`audioEffectProcessor.ts:19-40` 接收这些消息。`wasmEffectSdk.ts:37-175` 调用 `_EffectCreate`、`_EffectCommand` 和 `_EffectProcessBuffer`；未准备好或处理失败会旁路原始声道。
4. `main/src/services/player/audioEffect/intelligentAudioEffectFetcher.ts:10-133` 从曲目响应的 `track_player.audio_effects.intelligent` 找配置 URL，使用内存和 CacheStorage 缓存，并合并同一曲目的并发请求。`player.ts:226-251` 在曲目配置未到时可使用全局兜底配置。
5. `main/src/renderer/compositions/audioEffect.ts:18-22` 从 `appSettings.audio_effect` 读取可用预设。独立的本机窗口操作记录了截图中的九种选择及原选中项；证据在 `output/rea-upgrade-2026-10-12/soda-selected-*.png` 和 `runtime-selection-actions.json`。这只能证明界面可选择，不能证明输出 PCM 具体变化。本机汽水窗口最后恢复为原先的 3D 选择并最小化，见 `restore-confirmation.json`。

## 对 NASMusicBox 的实际指导

将音频解析、首段准备、队列预测和视觉取色拆开；当前播放优先于下一首的网络工作。NASMusicBox 采用只准备**实际下一首**、最多 2 MiB 前缀、32 MiB 内存上限的独立取舍。跨 QQ/YouTube 的保守同曲合并、地址刷新和历史游标属于 NASMusicBox 自行设计，并非从汽水包中抄得。

九种音效由 Web Audio 独立实现。汽水的 DSP 数值配置、实际 WASM 算法和处理后的 PCM 没有恢复。旧版 REA 对该 WASM 导入仅标记为静态引用，定向追踪没有原生 handoff，因此没有借 Ghidra 推断音效参数。现有样本测试证明 NASMusicBox 的九种输出确实不同；**无法证明与汽水同名预设的听感一致**。本机没有采集同片段、匹配响度的汽水处理结果，也没有完成真人桌面音箱盲听，后续调音应使用这些材料。
